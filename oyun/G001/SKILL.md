# Fixed-timestep game loop scheduler (MainLoop.js animate)

Given display frame timestamps, computes exactly what a fixed-timestep game loop does each frame: how many physics updates run, the render interpolation factor (alpha), the moving-average FPS and the 240-update panic guard, as in MainLoop.js. Used to choose the physics step and prove the loop stays stable on slow and fast screens.

MCP server name: `oyun-dongusu`; tool: `skillpack_g001`.

## When and how to use

Pass the requestAnimationFrame timestamps you want to test (for example 60 Hz, 30 Hz, a 400 ms stall) and the physics step. The first timestamp is the start frame (draw only). Read updates/alpha per frame and panic_frames.

Read manifest.json for the exact schema; do not guess missing data, coerce types or invent values. Exactly one JSON object is read from stdin; one JSON result is written to stdout. Success: `{ "ok": true, "result": {...} }`. Failure: `{ "ok": false, "error": {"code": "...", "message": "..."} }`, exit status 2.

## Place in the game-building flow

Step 9 (döngü kontrolü): confirm the chosen physics step (default 1000/60 ms) runs 1 update per frame at 60 Hz, catches up at 30 Hz, and that a tab-switch stall triggers panic + discard instead of a spiral. The step value is written into the HTML (G012), whose embedded loop is the upstream mainloop.min.js.

## Scope and failure

Simulates the scheduler only, not the work done inside update/draw. Timestamps must be non-decreasing. fpsAlpha=0.9 and fpsUpdateInterval=1000 ms are the upstream defaults and are not configurable. max_fps=0 (stop) is not supported.

## Faithfulness

Line-by-line port of animate(): minFrameDelay skip, frameDelta accumulation, fps exponential moving average every >1000 ms, update loop with the 240-step panic break, draw(frameDelta/timestep). start() is modelled as the first timestamp drawing once and resetting lastFrameTimeMs/lastFpsUpdate. discard_on_panic models the documented end() pattern calling MainLoop.resetFrameDelta().
